# Pi geometry plugin bridge — project-scoped preview only

This guidance applies only when the project explicitly selects the local geometry package. The five skills remain in their first-party source directories; do not copy their XML databases into another tracked path. Pi presents each loaded skill's absolute `location` and tells the model that relative references resolve against that skill's directory.

When a geometry skill names `${CLAUDE_PLUGIN_ROOT}/skills/<skill-name>/<file>`, Pi does **not** substitute that Claude token. Instead, resolve `<file>` relative to the **loaded skill's location**: for `python-rhino-grasshopper`, the three XML signature files live in `resources/` next to its `SKILL.md`; for `rhino-e2e-testing`, `resources/` and `scripts/` live next to its `SKILL.md`. Verify the requested file exists before read/grep or running any script; use the resolved absolute path from the loaded skill, never the consuming project's cwd or a guessed filename. If the skill location or resource is unavailable, stop and report a blocked lookup rather than guessing an API signature or running a mutating probe. Never run Rhino/GH or install Rhino dependencies merely to verify resource paths.

The `geometry-validator` child is **not configured** in the three-role Pi pilot. Any review must use the configured report-only Pi auditor with raw orchestrator-captured evidence; it cannot execute Rhino tests. The Claude `model:` frontmatter does not select a Pi model. Project trust and an auditor tool allowlist are not an OS sandbox. This bridge adapts path/role assumptions for an explicitly selected project only; it does not approve geometric correctness or deploy any user-level resource.
