# Pi role-dispatch pilot

Source-only pilot for strategist, coder, report-only auditor, scribe (declared docs writer; read-only `/explain` profile), optional read-only explorer and a bounded four-child advisory council (`/council`). `/sync` and `/handoff` run in the main session. The current source supports detached explorer, strategist and auditor jobs; it is not installed into Claude or Codex. Activating source changes in Pi needs a separate, approved Pi-only release; the PI-9 changes below have been installed once into a maintainer Pi agent directory that way, and other installations are unaffected until their own release.

## Setup

Requires Pi 1.4.0+, Node.js 22.19+, and credentials for the models you select. Copy [`tests/fixtures/pi-role-policy.json`](../tests/fixtures/pi-role-policy.json) to a **private file outside the public source tree**, substitute your own five exact `provider/model` IDs and three role assignments, then set `PI_ROLE_POLICY_PATH` to its absolute path. Missing or invalid policy prevents the extension from loading; no ambient model is selected as a fallback. The public fixture retains the three-role baseline for compatibility. To enable `/explain`, add a `scribe` role to your **private** policy with an already allowlisted exact model, `thinking: "low"`, and `tools` as a subset of `read`, `grep`, `find`, `ls`, `edit`, `write` (no `bash`; `/explain` forces the read-only profile regardless); without it the role dispatch stops. To enable the read-only explorer, add an `explorer` role (an already allowlisted exact model, e.g. a Haiku-class model with `thinking: "medium"`) with exactly `tools: ["read", "grep", "find", "ls"]`; the validator rejects any other tool set, and rejects a legacy `concierge` key with a migration message, so migrate the key before loading this source. `/sync` and `/handoff` run in the main session and need no child. Do not put API keys in the policy.

For a local Git Bash session, after creating your private policy at the example path:

```bash
export PI_ROLE_POLICY_PATH="$HOME/.pi/agent/role-policy.json"
pi -e ./pi/extensions/guard.ts -e ./pi/extensions/session-observability.ts -e ./pi/extensions/role-agent.ts
```

Run Pi from a trusted pilot project; point all three `-e` flags to absolute source paths when outside this repo. The parent loads the guard and bounded session observability explicitly; shell/write-capable role children receive **only** the guard (plus `role-guard.ts` for `edit`/`write`, and `auditor-recorder.ts` for the record profile), with ordinary extension discovery disabled. The report-only auditor retains its no-shell/no-write tools; its separate `record` profile adds only `pi_record_verification` (see Auditor recording). Observability reads `Artifacts/.agent/current_task.md` once per session (≤2,000 B) when present; it does **not** validate that file's age, so verify its objective against the active TODO before acting. It writes completed-tool **metadata only** to an existing project's `Artifacts/.agent/pi-audit.jsonl` (64 KiB cap, recent validated rows retained). It records tool type/outcome/time, never command, tool arguments, file path or result content; it does not audit user-typed direct shell or child-internal calls and adds no automatic completion nag. Running from source with `-e` flags is a preview, not a global installation or OS sandbox. `/pi-roles` shows the loaded private assignments. Ask Pi to call `pi_role_agent` with `{"role":"strategist","task":"Plan a bounded change"}`; the other roles include `coder`, `auditor`, `scribe`, configured `explorer`, the explicit `council-perspective` route, and `pi_council` (three perspectives plus advisory synthesis).

## Role tools and writer ownership (PI-9)

Role maxima are fixed in `pi/lib/role-policy.mjs`; a private policy may only narrow them. Explorer and auditor: `read`, `grep`, `find`, `ls`. Strategist and scribe: those plus `edit`, `write`. Coder: those plus `bash`, `edit`, `write`. Scribe has no shell. Policy load rejects duplicate or out-of-maximum tools, a non-exact explorer set, and role keys other than strategist, coder and auditor, with optional scribe and explorer (legacy `concierge` gets a migration message).

Effective profiles (`buildAgentArgs` in `role-policy.mjs`):
- `read-only` (strategist, coder, auditor, scribe): `read,grep,find,ls` only. `/explain` always requests this for its scribe child.
- Detached explorer, strategist and auditor jobs: read-only (`explorer-jobs.mjs`). No detached writer.
- `record` (auditor only): `read,grep,find,ls` plus `pi_record_verification`; no `edit`/`write`.
- Council and packet routes use read-only or no-tool profiles.
- No profile: the role's configured tools, which may include `edit`/`write`.

Children with `edit`/`write` load `role-guard.ts`; children with `bash`, `edit` or `write` load `guard.ts`.

**Policy source.** A project-root `role-ownership.json` overrides; otherwise the global file in `PI_CODING_AGENT_DIR` or `~/.pi/agent/` is used (`role-ownership.mjs`).

**Fail closed.** A present but invalid or inaccessible override, or an invalid or missing global file, yields no ownership and refuses every writer mutation (`role-ownership.mjs`, `role-guard-core.mjs`). Unsafe path forms (UNC, drive-relative, `..`, trailing dot or space, 8.3 tilde, device names), links, junctions and multi-link targets are refused.

**Schema (version 1).** Exactly `version`, `roles`, `protected`, `approvalLinePrefixes`. `roles` holds exactly `strategist: {plans, todos}`, `coder: {residual: true, generated}`, `auditor: {todos}`, `scribe: {docs}`. Globs use `*` within a segment and `**` as a whole segment; `\ : ! [ ] { } ( ) ? + | ^ $`, a leading `/`, and `.`/`..` are rejected. Each auditor TODO pattern must also be a strategist TODO pattern. Cross-owner overlap detection is heuristic.

**Protected floor** (never child-writable): `Artifacts/.agent/**`, `Artifacts/BACKLOG.md`, `Artifacts/learnings/**`, `Artifacts/GLOBAL_INBOX.md`, root `role-ownership.json`, `**/bulk-read-approval.json`, `**/bulk-read-ledger.jsonl`, `**/bulk-read-ledger.lock`, the global ownership file, and the policy's `protected` list (`role-ownership.mjs`).

**Owner classes** (`authorizeMutation` in `role-ownership.mjs`):
- Strategist (`plans`, `todos`): every existing task ID, marker and suffix is kept; verified task lines are immutable; no deletions; new tasks are `[ ]` with no suffix; BOM, final-newline state and approval blocks are preserved (`todo-ownership.mjs`).
- Auditor (`todos`): markers change only through the recorder below. `role-guard` refuses the auditor role.
- Scribe (`docs`): approval blocks are immutable; task-shaped text in docs has no TODO authority.
- Coder: `residual` (any path no other class owns) and `generated`. Evidence (`Artifacts/Evidence/**`) is Coder create-only (`wx`); it is never edited or overwritten.
- Coder `bash` is not covered by this guard (known gap; see Limits).

**Parent override interview.** Before a project override is written, the Parent checks that the layout matches the declaration, asks one question at a time, proposes exact contents, and writes only after explicit approval. Always ask: "Does any build/test step regenerate docs or planning files?" If yes, those generated paths become Coder-owned and conflicting scribe, strategist or auditor patterns are narrowed; ambiguous overlaps are refused.

## Pi prompt templates

`prompts/{blueprint,implement,audit,explain,council,triage,grill,registry-audit,snapshot,sync,ingest,learn,clean,graduate,skill-graph,sweep,agents-md,docs,handoff}.md` can be selected for one Pi process with repeated `--prompt-template <absolute-source-path>` flags. Selecting them this way does **not** install them into your user-level Pi prompts; an approved Pi release does (the PI-9 release installed them in a maintainer Pi agent directory). In a disposable consuming project, load the pilot extension with `-e <absolute-path-to-role-agent.ts>`, set the private policy environment variable, and add only the templates you are testing. Then invoke a selected `/name` command in Pi. `/blueprint`, `/grill` request a strategist child; `/implement`, `/triage` request a coder child; `/audit`, `/registry-audit`, `/snapshot` request a report-only auditor child with main-session captured evidence. `/explain` requests a read-only scribe child and its `codebase-navigator` skill; the child must be observed, not inferred from the template. `/sync` and `/handoff` run in the main session on a real project (no child; they replace the legacy `source-command-sync`/`source-command-handoff` skills, which can be excluded in Pi settings); `/ingest`, `/learn`, and `/clean` remain main-session workflows; `/clean` requires explicit confirmation before any deletion. `/graduate` is source-repo-only and report-first, `/skill-graph` uses a strategist, and `/sweep` uses only configured pilot child roles plus a main-session docs scan. `/agents-md` is the Pi report-only successor to Claude's `/claude-md`; it does not invoke the Claude plugin. `/docs` updates *repository* docs with `doc-updater` in the main session, not the separate user-level `/skill:docs` connector. Pi `/handoff` is **local-state-only** by user decision: it writes the current-task pointer (≤2,000 UTF-8 bytes), the brief (≤16 KiB) and, for a real decision, the decision log, then reports backup pending. TODO `[x]` markers, commit/push and backup remain outside it. GitHub backup is a separate authorized action; the existing Claude/Codex `/handoff` push requirement is unchanged. If the extension is missing, child-routed templates must stop rather than claim a role was dispatched.

A project-local `AGENTS.md` and optional Pi global context are separate from prompt templates. The global proposal lives in `Pi-global.md` at this repo's root; it includes eight **Pi-specific common-rule summaries**, not auto-loaded copies of Claude `rules/common/`. In a disposable consumer, explicitly preview that source file with `--append-system-prompt <absolute-path-to-Pi-global.md>`; without that flag the preview is absent. Running from source installs neither it nor these templates; an approved Pi release installs `Pi-global.md` as `AGENTS.md` together with the templates. Raw test output and exit status must be retained by the main session in a file the auditor actually reads, including for an audit following `/implement`; only an explicit project authority rule permits transcribing the auditor's cited PASS into a TODO marker. Do not use legacy `/skill:source-command-*` wrappers as evidence of Pi-native isolated routing.

## Parent and Explorer routing

Parent reads directly by default; delegate only clearly large read-only scans to Explorer, with at most one batched call per investigation (self-contained, no follow-ups). Parent may inspect targeted files and cited excerpts; this is guidance, not enforcement of Parent access or model. Explicit no-child workflows take precedence: `/sync` and `/handoff` are no-child and run in the main session. If the Explorer binding is missing or unavailable, stop and ask; never impersonate the child.

Make the batched request a self-contained question list: Explorer does not see the Parent's context. No follow-up Explorer calls for the same scan or same investigation; recover from the persisted result instead (via `collect` for detached jobs). Each dispatch re-pays its own prefix, so several small calls can cost more than reading directly.

For successful routed results, the full result is persisted before bounded delivery in a six-field envelope: status, summary, artifacts, findings, blockers and next action. The envelope is at most 2,048 UTF-8 bytes; its reference identifies the persisted result and hash. Use targeted recovery of relevant cited excerpts, not wholesale rereads. Persistence or verification failure yields INCOMPLETE; partial text may be recoverable via `collect` with `recoveryOffset` for detached jobs. Persistence requires hard-link support and is not fsync-durable.

## Task accounting

With session observability loaded and a project state directory present, bind a task using `/pi-task bind <task> <model> <input> <output> <cacheRead> <cacheWrite>`; the four rates are USD per million tokens. Use `/pi-task status` to inspect, `/pi-task checkpoint` to record a checkpoint, and `/pi-task close` to close when no admitted work remains outstanding. Unknown usage and lower-bound totals are not complete costs; accounting is not acceptance, even when closed. Task accounting tracks admitted work and settlements independently of collection; session totals include successful job usage only on first collect and can omit uncollected or failed work.

## Workflow

`extensions/role-agent.ts` registers `pi_role_agent`, `pi_council`, the role job tool when an eligible role is configured, and an inspection command. `lib/role-policy.mjs` loads and validates the private policy; `lib/role-runner.mjs` starts a separate Pi process for each role, setting the exact provider/model, thinking level, and tool list. It checks the completed assistant message's **reported** provider/model and thinking level, aggregates usage across turns, and rejects mismatches. That observation does not prove the provider applied a particular reasoning budget.

Before requesting an audit, the orchestrator runs the appropriate tests, captures the **raw output and exit status** in a file accessible to the auditor, and gives the auditor that file path plus the code paths to inspect. The auditor can read evidence and source but has **no `bash`, `powershell`, `edit`, or `write` tools**. It must return INCOMPLETE if evidence is missing or stale; it cannot rerun tests itself. The coder still has shell and write access.

## Auditor recording and TODO markers (PI-9)

1. **Review first.** The report-only auditor reviews captured raw evidence and ends with one `VERDICT:` line. It has no edit or write tool.
2. **Record separately.** After a settled result, the Parent makes a separate `pi_role_agent` call with `role: "auditor"`, `profile: "record"` and the strings `todo`, `taskId`, `taskSha256`, `verdictRef` (`Artifacts/.agent/pi-results/<id>.result`), `verdictSha256`, `manifestPath`, `manifestSha256`. Do not pass `date`; the extension supplies the local date (`role-agent.ts`). The child reads the binding from `PI_RECORD_BINDING` and exposes `pi_record_verification`, which accepts **no arguments** (`auditor-recorder.ts`).
3. **Refusals** (`auditor-recorder.mjs`): non-auditor role; missing or extra binding keys; malformed paths, IDs or dates; a `verdictRef` outside `Artifacts/.agent/pi-results/`; an ineligible TODO or missing task; a task-line hash differing from `taskSha256` (stale); a hash-mismatched or linked result or manifest; a result that is not a settled PASS or FAIL (INCOMPLETE is never recorded); drift between read and write; PASS on an already `[x]` task; a second use of one recorder. Writes use an exclusive temp file and rename, under the in-process mutation queue.
4. **Suffixes written** (`todo-ownership.mjs`), changing only that task's marker and suffix:
   - PASS: `- [x] … — Auditor-verified YYYY-MM-DD (PASS; verdict=<dispatchId>; sha256=<64 hex>)`
   - FAIL: `- [ ] … — Auditor-reviewed YYYY-MM-DD (FAIL; verdict=<dispatchId>; sha256=<64 hex>)`
5. **Dry-run helper.** `node scripts/mark-verified.mjs <todo> <TaskID> <result-ref> [--root dir]` prints a one-line old/new diff for a PASS result and never writes. `--apply` is refused (exit 2). A top-level `Artifacts/TODO.md` is refused.
6. **Checker.** `node scripts/check-markers.mjs <todo>... [--root dir] [--strict]` is read-only. Statuses: `valid` (PASS suffix matches its result); `reviewed` (FAIL suffix on `[ ]`); `legacy` (`[x]` with no suffix, failing only under `--strict`); `missing-file`; `hash-mismatch`; `stale-task`; `invalid` (contradictory or malformed suffix, non-regular result, verdict mismatch); `ineligible` (whole TODO fails the parser). Exit 1 on any other status, 2 on usage errors. It detects after-the-fact edits only and cannot prove who wrote a result.

## Council routes (advisory)

`/council <question>` requests the `pi_council` tool after the main session supplies **one** regular, single-link synthetic evidence file in a trusted disposable project's `Artifacts/Temp/` and its lowercase SHA-256. The tool sequentially invokes strategist, coder and auditor read-only perspectives, then a separate GPT Sol/high read-only strategist-profile synthesis. It refuses absent/changed evidence, missing/oversized outputs and synthesis without GO/NO-GO, three perspective labels and an explicit disagreement. Each of at most four children has a ≤10-minute timeout; the session budget is ≤40 minutes. The synthesis is advisory, not an independent audit or a decision. Tool allowlists are not OS sandboxing; no decision-log, TODO, source or deployment authority follows from the verdict. The synthesis output is limited to 16 KiB and cites three independently obtained texts; citing labels is a structural check, not proof the reasoning is sound.

The lower-level perspective route is also available:

Call `pi_role_agent` with `role: "council-perspective"`, one `perspective` (`strategist`, `coder` or `auditor`), `task` as the question, an absolute `evidencePath` directly under a trusted disposable project's `Artifacts/Temp/`, and the **same** lowercase `evidenceSha256` for all three calls. Run these calls **sequentially**, not in parallel: each shares the one-expensive-operation gate with strategist/auditor jobs and synchronous calls; concurrent calls are rejected, not queued. Each call gets the existing private model/thinking binding but a fixed `read,grep,find,ls` profile; the normal coder remains writable outside this route. The source validator checks a regular single-link ≤64 KiB evidence file against the supplied hash before and after the call, and the runner requires a successful observed read of that exact path. The perspective contract is `pi/agents/council-perspectives.md`; do not infer a council synthesis, GO/NO-GO, task completion or decision-log change from three opinions. The bounded T7 route above owns synthesis. This is **not** OS isolation: reads remain unrestricted, provider credentials are inherited, and concurrent file replacement can race the hash check.

## Explorer and the retired concierge guard (routed pilot)

`pi_role_agent` with `role: "explorer"` runs an isolated child (`pi/agents/explorer.md`) with exactly `read,grep,find,ls`, `--no-extensions`, `--no-mcp` and `--exclude-tools mcp__*`. It returns cited context (file:line, search coverage, truncation and unresolved questions) and the runner reports bounded observed `toolCounts` and `successfulReads` (names and counts only). It has no `Artifacts/` or Git-evidence prerequisite. The runner rejects any observed non-read tool event, and a wrong model or thinking level; these are post-hoc checks on reported events, not a pre-execution sandbox. Reads are **not** confined to the project: provider credentials are inherited and the model can read sensitive files, so use trusted, non-secret projects and an OS/container boundary for untrusted work.

**Detached read-only jobs.** The user sees a metadata-only notification when a job finishes; it never starts a model turn. This notification is best-effort and appears only with an attached UI; headless and print modes are silent, while RPC may forward it to a client. `pi_explorer_job` is registered when any eligible `explorer`, `strategist` or `auditor` role is configured. It accepts `action`: `start`, `status`, `collect`, `cancel` and `role` on start; omitted role defaults to explorer. Detached strategist and auditor jobs are forced to the read-only profile at argument construction, and observed tool events are checked. Synchronous strategist calls may still hold `edit`/`write` (see Role tools). `start` returns an opaque job ID while the child runs; at most **two** jobs are active, and a third is rejected, never queued. One shared gate permits at most **one** strategist/auditor/council operation, including synchronous calls; an unconfirmed cleanup retains the gate. The tool stores at most 16 records in memory (4 KiB task, 64 KiB result, about 2 KiB error plus a truncation marker); collection returns a bounded envelope as a Pi session tool result.

Auditor starts require an absolute `evidencePath` under the current project's `Artifacts/` and a lowercase `evidenceSha256` of a JSON manifest: `{ "version": 1, "captures": [{ "path": "<capture path>", "sha256": "<lowercase SHA-256>" }] }`. The manifest is at most 64 KiB and names 1–64 unique nonempty, regular, single-link captures of at most 4 MiB each within `Artifacts/`. Capture paths may be absolute or project-relative. The manifest and captures are rechecked after execution and on collection; changed evidence yields an **INCOMPLETE** evidence status and text prefix, even though the job state can remain `succeeded`. The child reads live files, not a snapshot: changes restored before a recheck can escape detection. Source identity is only as strong as the supplied captures: include the source/diff identity and raw command outputs with exit statuses; the validator does not run Git. A returned verdict is advisory and cannot mark tasks complete.

Background strategist/auditor starts require `jobBudget` in the private policy and a rate for the selected model; otherwise they are denied before launch. Set `perJobUsd`, `perSessionUsd` and a `rates` object keyed by allowlisted `provider/model`, each with positive `inputPerMTok` and `outputPerMTok` in USD per million tokens; optional `cacheReadPerMTok` and `cacheWritePerMTok` default to the input rate. Use actual model rates, not secrets. Policy validation requires `0 < perJobUsd ≤ 10` and `perJobUsd ≤ perSessionUsd ≤ 50`. The pilot's approved $1/job and $3/session values must be **set in the private policy**; they are not automatic defaults. A reservation is made before start and settled from observed token usage independently of collection; failed, cancelled or unknown-usage jobs retain their reservation. Budget survives `/tree` but resets with a new extension runtime, including session replacement or reload. Late usage can exceed the reserved amount: this is **not a hard provider spending cap**. Synchronous strategist/auditor/council calls are gated but are not charged to this background-job budget.

**Tier-aware rates (`pi/lib/pricing.mjs`).** A rate may be flat (as above, unchanged) or tiered: `tiers` is an ordered list whose entries carry `upToPromptTokens` (inclusive, strictly increasing; the last tier has none) plus the four prices. The tier is chosen **per API request** from that request's `input + cacheRead + cacheWrite` and applies to every token class of that request, output included; a job or session total is the sum of per-request costs, and cumulative totals never pick a tier. Optional metadata: `status` (`verified` or `provisional`; absent is shown as unlabelled), `source`, `cacheWriteRetention` (which retention `cacheWritePerMTok` prices: `5m`, `30m` or `1h`) and `cacheWriteByRetention` (alternate prices, e.g. `{"1h": 4}`). Nothing is assumed: an unspecified or unpriced cache-write retention, or usage with no per-request breakdown (priced at the highest tier as an upper bound), is labelled an **estimate**, and verified, provisional and unlabelled dollars are totalled separately, never blended. Job costs print a suffix such as `(estimate, provisional rates)`; ledger `rateUsd` stays separate from `providerUsd`. Configure only rates and thresholds you have confirmed; an unverified Terra, Haiku or other rate belongs under `status: "provisional"`. Live policy files are not changed by this source.

Jobs use a ten-minute child deadline and own their cancellation; aborting the starting tool call or ordinary turn boundaries does not stop them. Session shutdown/reload and successful `/tree` navigation cancel jobs and discard their in-memory records; `/tree` can retain records requiring recovery or quarantined cleanup. Successfully persisted result and settlement files remain. Pi documents shutdown of the old runtime on session replacement; `/resume` and `/fork` remain unverified in this pilot. A crashed or hard-killed Pi process does not supervise children. Usage enters Pi session totals on the **first** collect only; failed, cancelled and uncollected jobs can be absent from those totals. A child whose cleanup cannot be confirmed holds its slot. Windows cancellation uses `taskkill` for the child tree; POSIX descendant cleanup is not implemented. These jobs are not an OS sandbox: reads are unrestricted and credentials are inherited. Live strategist/auditor background behavior remains unverified until separately approved probes.

`pi/lib/concierge-guard.mjs` is retained only as a compatibility denial: if `PI_ROLE=concierge` is ever set, `pi/extensions/guard.ts` allows `read`, `grep`, `find` and `ls` and denies every other tool, including `edit`, `write` and shell, whatever the project root; it never falls back to the parent guard. The earlier two-file write exemption and `pi/lib/concierge-evidence.mjs` were removed. No global install or live role route is authorized by this document; activating the explorer needs the source and a private policy that uses the `explorer` key to be installed together.

## Limits

- This is a pilot, not a migration of all commands, rules, skills, plugins, or hooks. A disposable Pi parent invoked the extension's `pi_role_agent` tool for a read-only scribe `/explain` and received a cited child result; a separate direct-child probe observed the configured private binding and read-only tool events. Earlier three-role fixture flow was driven through `runRole()` directly, not through the extension as a multi-agent workflow. Neither probe proves production reliability or full scribe documentation/editing work.
- A tool allowlist and the Pi guard are **not a security sandbox**. `read`, `grep` and `find` can access sensitive files beyond the task unless the operating environment restricts them; their contents may reach the provider. The scribe pilot is tested only in trusted disposable projects with synthetic, non-secret data. Model subprocesses inherit the Pi process environment, including credentials used to call their providers. The coder has `bash` and can access inherited keys; run only trusted tasks and projects. The guard sees Pi `tool_call` and user `!`/`!!` (`user_bash`) in processes that load it; it does not inspect shell scripts after launch, indirect writes or unguarded external processes. Dangerous direct shell asks for confirmation with a UI and denies without one. Keep stronger isolation in scope before global or unattended deployment.
- **Write scope (PI-2 B1):** the guard blocks `write`/`edit` whose resolved real path (links and junctions followed, new leaves checked through their nearest existing ancestor) is outside the launch directory, except the OS temp directory; UNC/extended paths and ambiguous dot/space segments are refused without touching the filesystem. Shell commands are **not** sandboxed. PI-2 S-B denies only the common destination operand of `cp`/`mv`/`install`/`rsync`/`ln`/`tee` when it resolves outside the launch directory or OS temp; interpreters (`python -c`, `node -e`), `$VAR` destinations, `xargs`/`find -exec` wrappers, hard links, TOCTOU and any other program that writes still escape it, and the complete fix is an OS-level container or sandbox. Uncovered: redirects to non-source paths, plain `rm`, non-777 `chmod`/`chown` and recursive deletes of any absolute path outside the project (not only under `/tmp`) stay uncovered. Paths are judged by mirroring Pi's own normalization (Unicode spaces, `@`, Windows Git Bash/MSYS/Cygwin/WSL drive forms, `~`, `file://`) and lexical resolution against the launch directory, then compared by real path; the filesystem is first touched only for the local launch and temp directories and the nearest existing ancestor of a non-UNC target. Residuals: a hard link inside the project that points outside is not detected; `TMP`/`TEMP`/`TMPDIR` define the temp exemption; a launch directory on a network drive or an extended-length `\\?\` path fails closed. A session that must edit another repository has to be launched there.
- The auditor's lack of shell prevents independent test reruns. A caller-supplied summary is not evidence: it must read captured raw output and compare it with the source itself.
- The runner uses a ten-minute default child deadline and a two-second force-kill grace period; the actual multi-minute deadline is not live-tested. An isolated Pi agent-directory preview and its rollback (prior bytes and absence restored; the `pi-retained/` checker intentionally kept) do not prove that the current source has been installed or that live rollback and cross-project behavior work.
- **PI-9 gaps:** Coder `bash` is not ownership-checked and can change others' files. Tool allowlists and guards are not an OS sandbox.
- **No cross-process lock or compare-and-swap:** drift checks and the mutation queue are in-process; another process can change a TODO or doc between check and rename.
- **Audit linkage:** the recorder hash-checks the manifest in its binding, but the job settlement does not link to that manifest.
- **Release checks:** the import closure is regex-based; the 20 prompt templates (the 19 listed above plus the internal `bulk-read-system.md`) and seven role prompts are hard-coded in `release-preview.mjs`, so a new template needs a code change. Ownership overlap detection is heuristic.
- **Live probes are limited.** The rehearsal and tests are not live probes. One bounded post-install acceptance run observed the five role bindings and writer-ownership refusals; writer children declined cross-role mutations on their own instructions, so tool-level refusal of another role's declared file is covered by tests only.
